# OCI Always Free VM 새 환경 설정 지시서

이 문서만 받은 AI 에이전트가 아래 OCI VM 생성을 실제로 완료하도록 작업한다. 단순 안내로 끝내지 말고, OCI에 로그인된 현재 상태와 리소스를 확인하고, 오류를 진단하고, 안전한 재시도를 이어가며, 끝에 모든 조건을 검증한다. 이 파일은 다음 환경에서 재사용할 설정 지침이므로 실행 결과나 세션별 상태를 덧붙이지 않는다.

## 목표와 완료 조건

- 리전: Japan East (Tokyo), `ap-tokyo-1`

- 인스턴스: `VM.Standard.A1.Flex`, \*\*2 OCPU / 12 GB RAM\*\*

- 부트 볼륨: \*\*200 GB\*\*

- 이미지: ARM 호환 Oracle Linux 9 (A1 Flex용)

- 네트워크: 로그인한 계정/리전에서 사용 가능한 VCN의 public subnet. 없으면 새로 구성하고 공개 IPv4 할당

- SSH: 사용자 PC에 쌍이 맞는 개인키와 공개키를 저장하고, 공개키를 인스턴스에 등록

- 비용: Always Free 범위 유지. 계정 업그레이드, 유료 shape, 유료 용량/서비스로 전환하지 않는다.

완료로 처리하려면 OCI에서 인스턴스가 `RUNNING`인 것을 확인하고, 실제 shape 설정이 2 OCPU / 12 GB인지, 부트 볼륨이 200 GB인지, 올바른 SSH 공개키가 등록됐는지, 사용자 PC의 개인키 파일이 공개키와 맞는지 확인해야 한다. 생성 요청을 제출했거나 인스턴스가 `PROVISIONING`인 것만으로 완료 처리하지 않는다.

이 작업 지시서를 사용자가 직접 전달해 작업을 요청한 경우 위의 정확한 설정으로 생성하는 권한은 이미 부여된 것으로 간주한다. 동일한 설정을 다시 확인받느라 중단하지 않는다. 다만 로그인, OTP, CAPTCHA, 보안 경고, 현재 플랫폼의 action-time 확인 정책이 요구하는 단계는 해당 정책을 따른다. 사용자가 로그인해야 하는 경우 로그인 화면에서 기다린다. 비밀번호나 OTP를 문서, 로그, 셸 명령에 저장하지 않는다.

## 완전히 새 계정/환경에서 시작

이 작업은 이전 계정, 이전 로그인 세션, 기존 SSH 키, 기존 네트워크, 기존 CLI 설정이 하나도 없다고 가정한다. 아래에 적힌 계정별 값은 예시로도 사용하지 말고 현재 로그인한 계정에서 다시 조회한다.

1. 사용자가 제공한 OCI 계정/초대 링크를 연다. 사용자가 로그인 및 MFA를 직접 완료할 수 있도록 로그인 화면에서 기다린다. 자격 증명, MFA 코드, 복구 코드 또는 세션 쿠키를 요청하거나 저장하지 않는다.

2. 사용자가 리전을 알고 있다고 가정하지 않는다. OCI Console의 리전 메뉴와 CLI의 `oci iam region-subscription list --all`을 확인해 로그인 계정에서 사용할 수 있는 리전을 보여준다. 이 작업의 목표 리전은 Tokyo (`ap-tokyo-1`)이므로 Tokyo 구독 여부를 직접 조회한다. 구독되어 있으면 Console 리전 메뉴에서 Tokyo를 선택한다. 구독되지 않았으면 계정 관리 권한이 있을 때 Tokyo 구독을 진행하고, 권한이 없으면 사용자에게 필요한 계정 관리자 조치를 구체적으로 알린다. 다른 리전으로 임의 변경하지 않는다.

3. Cloud Shell을 열어 사전 인증 CLI가 실제 로그인 계정에 연결됐는지 확인한다. `oci iam region-subscription list`와 `oci iam compartment list --include-root --all`로 현재 테넌시, Tokyo 구독 및 구획을 조회한다. `/etc/oci/config` 또는 다른 Cloud Shell 제공 설정을 사용할 수 있다. 문서 속 OCID나 이전 PC의 설정을 복사하지 않는다.

4. 새 계정에는 기존 인스턴스, Cloud Shell 작업, SSH 파일이 없다고 가정한다. 단, 시작 직전에 현재 계정과 Tokyo 리전에서 인스턴스, 볼륨, 네트워크를 직접 조회해 중복과 사용량을 파악한다. 이전 인스턴스가 없다는 이유로 과거 자원을 찾으려 하지 않는다.

5. 사용자의 PC에 새 RSA 4096 SSH 키 쌍을 아래 명시된 저장 경로에 만든다. 계정 간 키 재사용이나 다른 PC에 저장된 개인키를 추정하지 않는다.

6. 선택한 계정의 root compartment OCID, Tokyo availability domain, 호환 이미지, VCN 및 subnet을 직접 조회해 사용 가능 여부를 판정한다. 적합한 네트워크가 없다면 아래 네트워크 준비 절차대로 만든다. 사용자에게 OCID나 네트워크 이름을 묻지 말고 계정별 값을 하드코딩하지 않는다.

7. Always Free 자격, 사용량, 현재 서비스 한도와 A1 용량을 확인한다. 요청한 구성이 무료 자격이나 서비스 한도를 넘는다고 확인되면 유료 자원으로 진행하지 않는다. 무료 범위에서 해결할 수 있는 원인을 조사하고, 불가하면 선택지를 설명한다. 저장공간 확보를 위해 기존 리소스를 삭제해야 하면 리소스를 특정하고 사용자 승인을 받는다.

### 리전과 네트워크 발견·판정·생성

사용자는 리전, VCN, subnet, OCID를 미리 알 필요가 없다. AI 에이전트가 OCI 로그인 세션과 CLI를 이용해 현재 계정에서 찾아 검증하고, 필요한 네트워크가 없을 때 생성한다.

1. 로그인 테넌시와 root compartment OCID를 `oci iam compartment list --include-root --all`에서 찾고, Tokyo 구독을 `oci iam region-subscription list --all`에서 확인한다. Tokyo가 미구독이면 위 절차에 따라 구독한다.

2. Tokyo로 리전을 전환한 뒤 `oci iam availability-domain list --compartment-id <ROOT\_COMPARTMENT\_OCID> --all`, `oci network vcn list -c <ROOT\_COMPARTMENT\_OCID> --all`, `oci network subnet list -c <ROOT\_COMPARTMENT\_OCID> --all`을 실행한다. CLI 결과만으로 불명확한 라우팅/보안 설정은 Console에서 해당 VCN, subnet, route table, security list/NSG 상세를 열어 확인한다.

3. 기존 subnet은 다음을 모두 만족할 때에만 재사용한다: 같은 로그인 테넌시와 Tokyo 리전에 속함, 인스턴스의 compartment에서 사용 가능, 상태가 사용 가능(`AVAILABLE`), VCN의 route table에 인터넷 게이트웨이 경로가 있음, subnet의 public IPv4 할당이 허용됨. TCP 22 규칙은 기존 보안 설정을 읽어 확인한다. 생성에 실패하면 에러를 근거로 잘못된 subnet/네트워크를 교체한다.

4. 적합한 public subnet이 없으면 현재 리전의 기존 CIDR과 겹치지 않는 사설 CIDR을 고르고, OCI Console의 VCN Wizard에서 인터넷 연결이 있는 VCN과 public subnet을 생성한다. Wizard가 public/private subnet, internet gateway, route rule 및 security list를 함께 만들도록 설정한다. 이름/CIDR은 현재 리소스를 조회해 충돌하지 않게 정한다. 새 리소스가 무료 네트워킹 범위와 계정 정책 안에 있는지 확인한다.

5. 보안 규칙에 SSH가 필요하면 TCP 22 ingress를 추가한다. 사용자 공인 IP를 확인할 수 있으면 `/32`로 제한한다. 확인할 수 없을 때는 기존 규칙을 우선 이용하고, 외부 SSH가 꼭 필요하나 범위를 정할 수 없는 경우에만 기본 허용 범위를 사용자에게 설명하고 최소한의 필요한 규칙을 구성한다.

6. 인스턴스 생성 요청에는 검증된 public subnet OCID와 public IPv4 활성화를 지정한다. 네트워크 이름/OCID를 사용자에게 입력시키거나 이전 계정 값으로 대체하지 않는다.

## 계정에서 조회할 OCI 값

다음 값은 계정별/리전별이므로 실행 시마다 OCI에서 조회한다. 과거 문서나 세션에 보이는 OCID를 새 계정에서 재사용하지 않는다.

- 로그인된 tenancy의 root compartment OCID와 표시 이름

- Tokyo region subscription 상태

- Tokyo availability domain 목록

- 현재 리전의 Oracle Linux 9 ARM 이미지 OCID (`VM.Standard.A1.Flex`와 호환되는 `aarch64` 이미지)

- 사용할 VCN 및 인터넷 연결된 public subnet OCID

- 해당 계정의 A1 Flex 및 boot volume 관련 서비스 한도와 현재 사용량

조회 예시(응답을 확인해 실제 사용 가능한 OCI CLI 옵션을 적용):

```bash

oci iam region-subscription list --all

oci iam compartment list --include-root --all

oci iam availability-domain list --compartment-id <ROOT\_COMPARTMENT\_OCID> --all

oci compute image list --compartment-id <ROOT\_COMPARTMENT\_OCID> --operating-system 'Oracle Linux' --all

oci network vcn list --compartment-id <ROOT\_COMPARTMENT\_OCID> --all

oci network subnet list --compartment-id <ROOT\_COMPARTMENT\_OCID> --all

```

이미지 목록에서 Tokyo 리전의 Oracle Linux 9 ARM/aarch64 이미지를 선택하고, 생성 전에 shape 호환성을 확인한다. 계정에 하나 이상의 availability domain이 있으면 용량이 없을 때 각 도메인을 확인한다. fault domain은 요청에 넣지 않아 OCI가 배치하게 한다.

## SSH 키 처리 및 명확한 저장 위치

- 새 환경에 키가 있다고 가정하지 않는다. 사용자가 안전하게 가져온 기존 키를 명시하지 않는 한 사용자 PC에서 RSA 4096 키 쌍을 새로 만든다.

- 기본 키 이름은 `oci-tokyo-a1`로 한다. 생성 전에 대상 경로에 같은 이름 파일이 있는지 확인하고, 있으면 덮어쓰지 말고 다른 이름(`oci-tokyo-a1-2` 등)을 사용한다.

- \*\*Windows\*\*: 사용자 프로필의 `.ssh` 폴더에 저장한다. 예를 들어 `C:\Users\<Windows사용자명>\.ssh\oci-tokyo-a1`이 개인키이고, `C:\Users\<Windows사용자명>\.ssh\oci-tokyo-a1.pub`가 공개키다. 폴더가 없으면 `New-Item -ItemType Directory -Force "$env:USERPROFILE\.ssh"`로 만든 뒤 `ssh-keygen -t rsa -b 4096 -f "$env:USERPROFILE\.ssh\oci-tokyo-a1"`를 실행한다.

- \*\*Linux/macOS\*\*: `~/.ssh/oci-tokyo-a1`이 개인키, `~/.ssh/oci-tokyo-a1.pub`가 공개키다. `mkdir -p ~/.ssh && chmod 700 ~/.ssh` 후 `ssh-keygen -t rsa -b 4096 -f ~/.ssh/oci-tokyo-a1`를 실행한다.

- 사용자에게 최종 저장 절대 경로를 알려주고, 파일이 실제 존재하는지 확인한다. 개인키는 사용자 PC에만 남긴다. OCI에는 공개키만 등록하고, Cloud Shell에는 공개키만 임시 전송한다. 개인키는 OCI, Cloud Shell, 채팅, 문서, 로그에 절대 업로드/붙여넣기하지 않는다.

- CLI의 `--ssh-authorized-keys-file`에는 공개키 `.pub`의 복사본만 사용한다. Cloud Shell 재시작 시 임시 파일이 사라질 수 있으므로 매번 fingerprint를 확인하고, 없으면 로컬 `.pub`만 다시 전송한다.

- 마지막에 `ssh-keygen -y -f <개인키\_절대경로>`에서 계산한 공개키와 저장된 `.pub`가 일치하는지 검증한다. 키 본문은 출력/로그/최종 응답에 넣지 않는다.

## 진행 순서

1. 위의 새 환경 절차에 따라 사용자가 로그인/MFA를 마친 뒤 Console과 CLI에서 현재 계정 및 Tokyo 리전을 검증한다. Cloud Shell은 사전 인증 CLI 설정(`/etc/oci/config` 등)을 제공할 수 있으므로 특정 홈 디렉터리의 설정 파일이 없다는 이유만으로 멈추지 않는다.

2. `oci compute instance list -c <root-OCID> --all --output json`으로 최신 인스턴스를 확인하고, `pgrep -af 'oci-retry.sh|oci compute instance launch'`로 활성 생성 프로세스를 확인한다. 동일한 인스턴스나 활성 루프가 있으면 중복 생성하지 않는다.

3. 현재 Always Free 용량과 스토리지 한도를 확인한다. `oci compute compute-capacity-report create --help`를 참고해 A1 Flex 2 OCPU / 12 GB를 조회한다. 필요하면 shape availability 항목마다 `faultDomain`을 지정해 세 fault domain을 각각 확인한다. 사용 가능한 capacity가 없으면 자동 재시도 규칙을 따른다.

4. 사용자 PC에서 만든 공개키(개인키 경로와 공개키 경로를 확인)와 검증된 VCN/public subnet을 준비한다. `--ssh-authorized-keys-file`을 쓸 경우 공개키만 Cloud Shell 임시 파일(예: `/tmp/oci-authorized.pub`)로 전달한다.

5. 같은 표시 이름의 인스턴스가 없는지 확인한 뒤 아래 요청을 보낸다. 재시도 스크립트 시작 시 이름을 한 번 정하고, 모든 재시도에서 같은 이름을 사용한다.

```bash

NAME="oci-a1-free-$(date +%Y%m%d-%H%M%S)"

```

```bash

oci compute instance launch \

--compartment-id '<ROOT\_COMPARTMENT\_OCID\_FROM\_CURRENT\_ACCOUNT>' \

--availability-domain '<TOKYO\_AD\_FROM\_CURRENT\_ACCOUNT>' \

--display-name "$NAME" \

--shape 'VM.Standard.A1.Flex' \

--shape-config '{"ocpus":2,"memoryInGBs":12}' \

--image-id '<ARM64\_ORACLE\_LINUX\_9\_IMAGE\_OCID\_FROM\_CURRENT\_ACCOUNT\_REGION>' \

--subnet-id '<PUBLIC\_SUBNET\_OCID\_FROM\_CURRENT\_ACCOUNT\_REGION>' \

--assign-public-ip true \

--boot-volume-size-in-gbs 200 \

--ssh-authorized-keys-file '/tmp/oci-authorized.pub' \

--wait-for-state RUNNING \

--wait-interval-seconds 30 \

--max-wait-seconds 1200

```

## 반복 재시도 규칙

사용자는 용량이 생길 때까지 반복 재시도를 요청했다. 실행 중인 Cloud Shell 프로세스가 있으면 그 프로세스를 이어서 확인하고, 두 개의 루프를 동시에 돌리지 않는다. 프로세스가 없고 같은 이름의 인스턴스도 없을 때만 재시도 루프를 새로 시작한다.

- 각 시도 전 같은 표시 이름의 인스턴스가 있는지 조회한다. 인벤토리 조회가 실패하면 결과를 빈 목록으로 간주하지 말고 중단해 원인을 진단한다.

- 각 시도는 하나씩 순차 실행한다. 요청이 아직 응답 대기 중일 때 다른 Create를 제출하지 않는다.

- `Out of capacity`, `Out of host capacity`, `TooManyRequests`, HTTP 429, 또는 속도 제한 오류에만 대기 후 재시도한다.

- 용량 부족이면 최소 5분, `TooManyRequests`/429이면 최소 10분 대기한다. 429가 반복되면 대기 시간을 더 늘린다. 반복적인 60초 재호출은 하지 않는다.

- 권한, 잘못된 이미지/shape, 서브넷, 한도, 계정/구획 같은 오류는 자동 반복하지 말고 구체적인 원인을 해결한다. 유료 전환은 하지 않는다.

- 오류가 애매하거나 요청이 타임아웃되면 먼저 인스턴스 목록을 조회한다. 같은 이름이 나타났다면 다시 만들지 말고 상태 확인으로 전환한다.

- 진행 상태를 사용자에게 자주 반복하지 않는다. 성공, 실제 오류/전략 변경, 사용자 조치 필요 시에만 짧게 알린다. 독립 조사에는 helper agent를 사용할 수 있지만, 실제 OCI UI/인증 세션은 현재 PC의 주 에이전트가 다뤄야 할 수 있다.

현재 Cloud Shell이 살아 있으면 우선 아래로 확인한다.

```bash

pgrep -af 'oci-retry.sh|oci compute instance launch'

tail -n 30 /tmp/oci-retry.log

```

## 생성 후 검증

최신 인스턴스 목록/상세 정보를 사용해 다음을 확인한다.

- `lifecycle-state`가 `RUNNING`

- `shape`가 `VM.Standard.A1.Flex`

- `shape-config.ocpus`가 `2`, `shape-config.memoryInGBs`가 `12`

- `bootVolumeSizeInGbs` 또는 연결된 boot volume의 실제 크기가 `200`

- SSH metadata에 방금 준비한 공개키가 등록됨

- 필요한 경우 VNIC에 public IPv4가 붙음

- 로컬 개인키가 존재하며 공개키와 일치함

CLI 권한 또는 필드 조회가 불편하면 Console의 인스턴스 상세 페이지와 Boot volume 상세 페이지에서 같은 값을 검증한다. 모든 조건이 증명되기 전에는 작업을 완료 처리하지 않는다.
